校园网 Dr.COM 客户端部署与 11 GB syslog 治理

文中账号、密码、MAC 均以占位符代替，静态地址为示意值；请以自己登记到的信息为准。

1.问题提出

学校学生宿舍的有线网使用基于 Dr.COM 的认证。Windows 下只要装上那个蓝绿色的官方客户端（Drcom）就能登录，但这套客户端只有 Windows 版，Linux 上没有对应程序。于是出现了一个很具体的困境：网络登记照做、静态地址照填，可就是在 Linux 里连不上。

我按学校流程做了三件事：在线上登记房间端口号（每个网口对应一个专属号）、绑定自己的校园网账号、填写电脑的 MAC 地址，随后拿到了一组静态 IPv4 地址和学校 DNS。在 Windows 上把这套地址配好、再打开 Dr.COM 客户端，认证就能通过。问题在于，我日常的开发环境是 Ubuntu，不可能为了一次认证单独留在 Windows 里。

后来在学长的社团论坛帖里看到，他们维护着一个开源项目 scutclient，专门在 Linux 上复刻这套认证流程。这篇文章记录的就是从发现它，到把它跑通、做成开机自启服务，最后治理它带来的日志问题的完整过程。

项目地址：scutclient，讨论出处：SCUT 开源社区论坛帖。

2.先区分：认证与编址是两件事

在动手之前，需要先把一个很容易混淆的点理清，否则后面的报错会很难定位。

论坛帖里给了很关键的说明：Drcom 拨号的本质，是基于 EAPoL 魔改的认证协议，加上基于 UDP 包的心跳保活机制。 这里其实包含了两个彼此独立、又都必须正确的环节：

  • 认证：发生在二层（L2）。客户端在网口上直接收发 802.1X 的 EAPoL 帧，向认证服务器证明“这个 MAC + 账号是登记的”。这一步和 IP 地址无关，只要网口物理链路是通的，帧就能到达交换机。
  • 编址：发生在三层（L3）。只有把登记到的静态 IPv4、网关、DNS 配到认证用网口上，认证通过后的流量才有正确的源地址，才能真正跑出校园网。

很多人（包括当时的我）会把这两件事当成一件事：既然认证是“登录”，那配好地址再点登录就行了。实际上它们各自会独立报错，而报错信息又都不那么直白。后文会看到，我踩的每一个坑，基本都能归到这两类里。

scutclient 是 SCUT Router Group 用 C 写的一个最小实现，采用 AGPL-3.0 许可，可以编译成不依赖外部运行库的二进制，也提供了 OpenWrt 的 ipk 包。它做的事情就是把上面那套 EAPoL 认证和 UDP 心跳重新实现一遍。

7.账号密码不该出现在命令行上

服务第一次跑起来后，systemctl status 显示的命令行让我警觉：

密码是明文出现在进程命令行（argv）里的。原因在于：服务单元里写的是 --password ${SCUT_PASSWORD}，systemd 会把变量展开成真实值再拼进命令行，于是 ps、systemctl status、journalctl 全都能看到。

这里要区分两个东西：命令行的 argv，和进程的环境变量。 scutclient 原本只支持从 --password 参数读密码，所以密码必然落到 argv。要避免它，就得让程序改从环境变量读——而 systemd 的 EnvironmentFile 恰好就是设进程环境变量的。

必须诚实地说清楚边界：这只是把密码从“人人可见的 argv”挪到了“权限受限的环境变量”，并不等于密码变得绝对安全。密码本身仍以明文存在配置文件中——这是 scutclient 只能命令行传参的设计决定的。此外，调试过程中密码已经在我的终端历史与日志里出现过，所以事后我把密码改掉了。

8.十一 GB 的 syslog 是怎么来的

真正让我下决心治理的，是磁盘。某天检查系统时发现 /var/log/syslog 异常膨胀，一度达到 11 GB；同时 systemd journal 也占到了 500 MB 左右。

排查后原因很直接：scutclient 的日志级别默认是 INF，而它每约 13 秒就会打印一次心跳日志。 登录成功后，日志会稳定地产生这样的内容：

这里需要区分两个容易混为一谈的东西：

  • journal（journald）：systemd 的日志系统，服务进程的 stdout/stderr 默认都被它捕获。
  • syslog（rsyslog）：传统的日志系统，/var/log/syslog 就是它写出来的。

scutclient 本身并不调用 syslog()。但它同时把日志写进了两处：/tmp/scutclient.log（文件）和 stdout（printf）。作为 systemd 服务运行时，stdout 进入 journal；而在我的系统上，journal 又被转发给 rsyslog，最终落进 /var/log/syslog。一条心跳日志，经过这么一条链路，就同时污染了三个地方。

换句话说，磁盘被塞满不是因为“认证出了问题”，而是因为一个需要 7×24 常驻的程序，默认开启了逐次心跳的 INFO 日志。这是长期常驻服务很容易忽略的一类成本。

路径 作用

最终达到的状态：

  • 以普通用户身份运行，仅依赖二进制的 CAP_NET_RAW 能力；
  • 开机自动启动，退出后自动重启；
  • 账号密码不出现在命令行（ps 不可见）；
  • 心跳日志静默，syslog/journal 不再膨胀；
  • 随时可回滚：停用服务、去掉 setcap、清空配置文件即可。

11.总结

这次折腾的门槛其实不高，真正花时间的是把几个被默认混在一起的概念拆开：

  1. 认证（L2）与编址（L3）是两件事。 前者是 EAPoL 帧，后者是静态 IP；not allowed to login using current IP/MAC address 这种报错，往往问题出在后者。
  2. root 与文件能力是两件事。 一个只需要 CAP_NET_RAW 的小工具，用 setcap 比用 sudo 更精确，也顺带避免了日志属主错乱。
  3. argv 与环境变量是两件事。 变量在命令行里会被展开成明文，这是“全局变量”最容易踩的泄露点。
  4. journal 与 syslog 是两件事。 服务的 stdout 先进 journal，再可能被转发到 rsyslog；一个常驻程序的心跳日志，会沿着这条链路同时污染多个位置。

还有一个更朴素的教训：需要长期常驻的服务，日志级别要从一开始就设计好。 scutclient 的默认 INF 级别对人交互使用完全合理，但对 7×24 运行来说，每 13 秒一条心跳日志就是持续不断的磁盘消耗。让它“跑起来”只是第一步，让它“安静地、可控地长期跑”才是真正的部署。

最后仍然要说明：本文的方案依赖我的具体环境（Ubuntu 24.04、NetworkManager、systemd 255），不同学校、不同版本的 Dr.COM 服务器协议细节可能不同，--cli-version、--hash 等参数也可能需要按实际情况调整。真正操作前，请以自己的登记信息和现场日志为准。
